# Audit

## Scope reference
[sprint.md](./sprint.md)

Sprint `001-full-audit-alignment` — full audit + end-to-end alignment of OutfitManager (OM) onto the modernized LordKuper sibling standard (EquipmentManager as the reference), delivered as a single sprint across seven workstreams: (W1) audit, (W2) per-project restructure, (W3) stack migration to the modern target (`.slnx` / .NET 10 SDK / `dotnet` / `jb` / Nullable / zero-warnings / Harmony 2.4.2 / Common 1.6 / NetAnalyzers 9.0.0), (W4) reuse-over-duplication against `LordKuper.Common`, (W5) optimization & simplification, (W6) unit test project (NUnit 4.x + FluentAssertions 7.x), (W7) rule conformance. - The **code side** (existing implementation, code-side gaps, risks, dependencies, related open stubs) is appended by the **Architect** in the marked placeholder sections.

### Build & analyzer feasibility

### Existing implementation (subsystem coverage)

- `OutfitManagerMod.cs`: `Mod` entry — logs version, `GetSettings<Settings>()`, `new Harmony(ModId).PatchAll(...)`, exposes the settings window. Minimal and correct.
- `Patches/JobGiverPatch.cs`: single Harmony **transpiler** on `JobGiver_OptimizeApparel.ApparelScoreRaw`. Scans the IL for the 5-opcode sequence `Ldloc_0 / Ldarg_1 / Callvirt Apparel.GetSpecialApparelScoreOffset / Add / Stloc_0`, then inserts a call to `ApparelScoring.GetPawnApparelWorkScore(pawn, apparel)` whose result is `Add`ed into the running score local. **Fail-soft**: if the pattern is not found it `Logger.LogError`s and returns the original IL unchanged (no throw). This is the entire integration mechanism and the central compat risk.
- `ApparelScoring.cs`: static scoring facade. `GetPawnApparelWorkScore` → lazy `Initialize()` (seeds stat ranges once by scoring every apparel `ThingDef` through every rule) → `GetApparelWorkScore` → `* Settings.WorkTypeScoreFactor`. Per-apparel caches held in a `ConditionalWeakTable<Apparel, ApparelCache>` (weak keys → destroyed apparel GC'd automatically — already a good memory pattern, the "apparel cache fix" in recent git history).
- `ApparelCache.cs`: `: ThingCache` (Common base, quadrum/`HoursInQuadrum` window). Caches per-work-type scores in a `Dictionary<string,float>`; `GetWorkTypesScore` returns the weighted sum over the pawn's normalized work-type weights.
- `WorkTypeHelper.cs`: `GetNormalizedWorkTypeWeights(pawn)` — derives per-active-work-type weights from `pawn.workSettings` priorities, normalized to sum 1; skips work types with no rule or no stat weights; guards `workSettings == null`.
- `Settings*.cs` (4 files, `partial class Settings : ModSettings`): General tab (a single clamped `WorkTypeScoreFactor` float slider, default 2f, range 0–5) + Work Types tab (rule selector + stat-weight editor rendered entirely by Common's `WorkTypeThingRuleWidget.DoWidgetTab`). Rules persisted via `Scribe_Collections.Look(..., LookMode.Deep)`. `InitializeWorkTypesSettings` de-dups rules, seeds a rule per work type, then merges `WorkTypeThingRule.DefaultRules`.
- `Logger.cs` / `Resources.cs` / `SettingsTabs.cs`: thin `Common.Logger` wrapper; centralized keyed-string surface (6 keys, `ModId`+`nameof`-derived); 2-value tab enum. All clean.

### Nullable migration — measured cost (W3)

- **The annotation/NRT surface is trivial.** Enabling `Nullable enable` requires: (1) remove the single `[NotNull]` at `ApparelCache.cs:24` (becomes the non-nullable `Apparel apparel` param — `ThingCache`'s base ctor already throws `ArgumentNullException` on null, so the contract is preserved); (2) annotate the handful of legitimately-nullable locals/fields surfaced by the flip. OM **already uses modern C# idioms** (file-scoped namespaces, collection expressions `[]`, target-typed `new()`), and Common's `WorkTypeThingRule`/`ThingCache` are **already `Nullable enable`**, so OM's consumption sites largely line up.
- **C-1 [nullable-migration, medium]** Enable `Nullable enable` on the production csproj and resolve the (small) set of NRT sites green under `TreatWarningsAsErrors`. The measured pre-existing annotation surface is 1 attribute; the real cost is the warnings the flip surfaces on Scribe-populated static fields (`_selectedWorkTypeRule`, `_workTypeRules`) and the `FirstOrDefault` nullable results in `ApparelCache`/`WorkTypeHelper`/`Settings_WorkTypes` — all small, mechanical (`?` + guard, `??=` for the Scribe list per `custom-coding-rules.md`). A clean compile-test of the flipped flag was not run here (legacy csproj cannot `dotnet build`); estimate is **well under 20 distinct sites** given the LOC and idiom baseline.
- **C-2 [nullable-migration/standard, low]** Replace the lone `[NotNull]` with real NRT and remove `using JetBrains.Annotations;` from `ApparelCache.cs` (it has no other JetBrains attribute). Leave the `using` + `[UsedImplicitly]` in the other 3 files.

### Reuse audit (W4) vs `LordKuper.Common` public surface

The inverse question (where does OM reimplement what Common provides?) returns **almost nothing** — OM was evidently written against the modern Common API from the start. Verified against Common source (`rimworld-common/Source/LordKuper.Common`): `WorkTypeThingRule` (public `[PublicAPI]`, already nullable), `ThingCache` (public, ctor `(Thing, float updateTimer)`, virtual `Update(RimWorldTime)`), `WorkTypeThingRuleWidget.DoWidgetTab`, `Common.UI.{Tabs,Fields}`, `RimWorldTime`, `StatWeight` all exist and are consumed directly.

- **RU-1 [reuse, informational — PASS]** `ApparelCache : ThingCache`, `Settings._workTypeRules : List<WorkTypeThingRule>`, the Work Types tab via `WorkTypeThingRuleWidget`, scoring via `WorkTypeThingRule.GetThingScore/GetThingDefScore`, time via `RimWorldTime`, logging via `Common.Logger` — all **consume Common's public surface correctly, no local reimplementation**. OM does NOT carry an `EquipmentManagerStatDefs`-style pass-through, a local `WorkTypeRule`, a local `StatRanges`, or a local `ItemCache` (EM's RU-1…RU-6 have **no OM analogue**). The "not a reimplementation of shared utilities" anti-pillar holds.
- **RU-2 [reuse, low]** `ApparelCache.GetWorkTypeScore` / `Update` both do `Settings.WorkTypeRules.FirstOrDefault(r => r.WorkTypeDefName == workTypeDefName)` — a linear rule lookup repeated per work type per apparel within a cache rebuild. This is OM-local logic (no Common equivalent to consume), but it is the one small inefficiency a reuse/simplification pass could address with a `Dictionary<string, WorkTypeThingRule>` index (cross-ref C-3). Not a duplication finding; a simplification one.
- **RU-3 [reuse, informational]** OM uses raw `DefDatabase<ThingDef>.AllDefs` in `ApparelScoring.InitializeStatRanges`. Common offers a `DefProvider` test seam in EM's audit; whether OM benefits is a testability note for W6, not duplication. No remediation.

### Correctness / simplification / performance (W5)

- **C-3 [simplification/performance, low]** `ApparelCache` does the same `Settings.WorkTypeRules.FirstOrDefault(...)` lookup in **two** places (`Update` pre-seeds every work type's score; `GetWorkTypeScore` re-looks-up on a cache miss). Since `Update` already populates `_workTypeScores` for **every** work type in priority order, the `GetWorkTypeScore` miss-path (`:37-42`) is effectively dead for any work type that exists in priority order — it only fires for a name not in `WorkTypeDefsInPriorityOrder`. Two redundant code paths compute the same value. Remediation: drop the eager `Update` seeding loop OR the lazy miss-path (keep one), and/or index rules by defName once. Behavior-neutral. Low severity.
- **C-4 [correctness, low]** `ApparelScoring.Initialize()` sets `_isInitialized = true` **before** `InitializeStatRanges()` runs (`:91-93`). If `InitializeStatRanges` threw mid-way (e.g. a malformed apparel def), the flag would remain set and stat ranges would be left partially seeded with no retry. Low likelihood (the loop only calls `GetThingDefScore`), but the order is fragile. Remediation: set the flag after successful init, or wrap fail-soft. Note: this mirrors the kind of first-init-seeding fragility EM hit in its C-4 — flag for a characterization test (W6).
- **C-5 [performance, informational]** `ApparelScoring.InitializeStatRanges` iterates **all** apparel `ThingDef`s × **all** work-type rules once on first score (`:99-105`); `ApparelCache.Update` iterates all work types in priority order per apparel per quadrum. Both are bounded and gated (the `ConditionalWeakTable` + quadrum window keep steady-state cost low); the weak-table caching is already a sound pattern.
