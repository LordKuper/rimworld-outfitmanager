ADR-0001 · Harmony-transpiler integration on JobGiver_OptimizeApparel.ApparelScoreRaw (fail-soft)

Context

OutfitManager's entire reason for existing is to fold a work-type-aware apparel score into RimWorld's native apparel-selection scoring. The vanilla method JobGiver_OptimizeApparel.ApparelScoreRaw computes the score a pawn assigns to a candidate piece of apparel; OM must add its own per-work-type contribution into that computation. There is no public extension point, virtual hook, or event on this method — the only ways to influence its result are a Harmony postfix (which can adjust the final returned value but cannot see the intermediate score local) or a transpiler that edits the method's IL directly.

The decision was made historically (this ADR is reverse-engineered from the shipped code in Source/Patches/JobGiverPatch.cs and Source/ApparelScoring.cs) and is being recorded now because the alignment sprint touches this integration surface (Harmony 2.3.6 → 2.4.2, restructure) and because OM is a published Workshop mod (id 1984694952) whose entire function depends on this patch applying correctly. Forces in play: (1) the injected score must enter the running score local at the same arithmetic stage as the vanilla special-apparel-score offset, so a postfix on the return value would not be equivalent; (2) RimWorld point releases can re-JIT/reorder the target method's IL; (3) other apparel-scoring mods may transpile the same method, shifting the IL shape OM matches against; (4) a published mod must never hard-crash the player's game on a failed patch.

Decision

Inject OM's work-type apparel score into vanilla scoring via a Harmony transpiler on JobGiver_OptimizeApparel.ApparelScoreRaw. The transpiler scans the method IL for the 5-opcode sequence Ldloc_0 / Ldarg_1 / Callvirt Apparel.GetSpecialApparelScoreOffset / Add / Stloc_0 and, at that point, inserts a call to ApparelScoring.GetPawnApparelWorkScore(pawn, apparel) whose result is Added into the running score local. If the anchor pattern is not found, the transpiler logs an error via the project Logger and returns the original IL unchanged — match-or-noop, never throw. The anchor is deliberately keyed on the Apparel.GetSpecialApparelScoreOffset callvirt (the most stable, semantically meaningful instruction in the window) rather than on raw local indices.

Consequences

Positive

  • OM's score enters the computation at the exact arithmetic stage as the vanilla offset — behaviourally correct, which a return-value postfix could not guarantee.
  • Fail-soft (match-or-noop) means a missed pattern degrades to vanilla behaviour, never a crash — appropriate for a published mod with a live player base (AC-33).
  • No new dependency or abstraction is introduced: the mechanism is a single Harmony transpiler over an API OM already consumes.
  • Anchoring on the GetSpecialApparelScoreOffset callvirt is more resilient to local-slot reordering than anchoring on raw Ldloc/Stloc indices alone.

Negative

  • A failed match disables OM's entire function silently from the player's point of view (no crash, but no work-type scoring) — a hard-to-notice loss unless surfaced (mitigation: a single diagnostic log line pairing patch-applied/patch-failed, emitted through the existing project Logger — log-facing only, not a player-facing UI surface; see Decision follow-up and risk R-C1).
  • The patch is coupled to a precise IL shape; a RimWorld point release that re-JITs or reorders ApparelScoreRaw, or another mod that transpiles it first, can break the match (risk R-C1).
  • The transpiler cannot be unit-tested without RimWorld IL context; only the fail-soft branch is cleanly characterizable (AC-27, risk R-C2/C-10).
  • The 2.3.6 → 2.4.2 Harmony bump touches the exact API this patch relies on (AccessTools.Method, CodeInstruction, OpCodes, CodeInstruction.Call) and must be re-verified in-game, not assumed (risk R-C3).

Published-mod flag (AC-33): this decision should be paired with a single diagnostic log line emitted through the existing project Logger (which wraps Common.Logger) that makes the patch-applied / patch-failed pairing explicit at startup, so a silent disablement is observable to maintainers from the player's log. This is a developer/log-facing diagnostic, not a localized player-facing UI string — it needs no Resources.Strings entry and no Keyed XML, so it does not violate the PRD no-UI / no-new-user-facing-string non-goal (conformant with AC-29 / AC-30). It is not a new self-check subsystem: the success path already logs "Applying JobGiver patch." and the failure path already logs an error — this change merely makes the pairing explicit and removes any #if DEBUG guard so the signal ships in release builds. Proportionate to a ~640-LOC mod: one log line, no new abstraction. The fail-soft contract itself introduces no save-format or settings change.

Alternatives considered

  • Harmony postfix on the return value of ApparelScoreRaw — rejected because it can only adjust the final score after vanilla math, not inject into the running score local at the same stage as GetSpecialApparelScoreOffset; the result is not arithmetically equivalent and risks double-counting/clamping interactions.
  • Throw on pattern-not-found (hard-fail) — rejected because OM is a published mod; a hard failure would crash or break colonies of players on any RimWorld update that shifts the IL, which is unacceptable degradation.
  • Anchor on raw local-slot indices (Ldloc_0/Stloc_0) only — rejected as the sole anchor because local numbering is the least stable aspect across re-JIT; the GetSpecialApparelScoreOffset callvirt is retained as the semantic anchor with the surrounding opcodes as confirmation.
  • Reflection-based wholesale method replacement (prefix returning false) — rejected because it would force OM to reimplement and maintain the full vanilla scoring body, maximizing both incompatibility surface and maintenance cost.

ADR-0002 · Legacy → modern stack migration

Context

OutfitManager still runs on the legacy build stack: a non-SDK OutfitManager.csproj (ToolsVersion 15.0, explicit <Compile Include> list, <TargetFrameworkVersion>v4.8</TargetFrameworkVersion>), packages.config-based restore, a VS-format .sln, Harmony 2.3.6, machine-specific hardcoded reference HintPaths, and no shared property layer. Its sibling mods (EquipmentManager as the reference) have already moved to the modern LordKuper house standard documented in stack.html and the 12 tech-reference/*.md files. The persistent design/ docs already describe that target state, so the docs intentionally lead the code; this sprint makes the code catch up.

Forces: (1) the legacy csproj cannot build under dotnet or run the jb cleanup/inspect flow defined in commands.yaml — only MSBuild/VS — so OM is unverifiable on the modern toolchain; (2) the hardcoded HintPaths (..\..\..\Games\Steam\… for RimWorld, ..\..\rimworld-common\… for Common, packages\Lib.Harmony.2.3.6\…) make the build non-portable and machine-bound (risk R-C5); (3) OM is published with a live player base, so the migration must preserve observable behaviour and save compatibility (AC-32, AC-33); (4) the zero-warnings policy is referenced but unenforced (WarningLevel 4, no TreatWarningsAsErrors). backward_compat=none waives an automated shim but does not waive the obligation to flag user-visible/save-affecting change.

Decision

Migrate OM to the modern sibling stack in a single end-to-end pass: convert the non-SDK OutfitManager.csproj to an SDK-style project (no explicit <Compile> list); migrate packages.config → PackageReference and remove the packages/ restore folder; convert the .sln → .slnx at Source/; introduce Source/Directory.Build.props carrying shared properties and env-var-resolved reference HintPaths (RIMWORLD_DIR / LORDKUPER_COMMON_DIR); build via the .NET 10 SDK dotnet build path with the jb cleanup/inspect flow; bump Lib.Harmony 2.3.6 → 2.4.2; pin LordKuper.Common at 1.6 and Microsoft.CodeAnalysis.NetAnalyzers at 9.0.0 (deliberate pins); and enforce zero-warnings via TreatWarningsAsErrors=true with a high warning level. The migration is strictly structural/toolchain — Scribe keys (WorkTypeScoreFactor, WorkTypeRules) and the persisted settings shape remain stable.

Consequences

Positive

  • OM builds portably on any machine via env-var-resolved HintPaths in Directory.Build.props — eliminates the machine-bound build (R-C5).
  • The modern dotnet build + jb flow becomes available, unblocking the test project (ADR/W6) and CI-style verification (AC-14, AC-31).
  • Zero-warnings is finally enforced with NetAnalyzers gating, raising the quality floor to the sibling standard (AC-28).
  • OM becomes structurally consistent with its sibling mods, lowering cross-project maintenance cost; the persistent design/ docs stop leading the code (reconciled per audit DM-1).
  • Deliberate version pins (Harmony 2.4.2, Common 1.6, NetAnalyzers 9.0.0) match the documented, tech-referenced target — no undocumented tech is adopted.

Negative

  • The Harmony 2.3.6 → 2.4.2 bump crosses a minor version on the exact API the transpiler uses; it must be re-verified in-game, not assumed (risk R-C3, ties to ADR-0001).
  • A green build now depends on RimWorld and rimworld-common being resolvable on the build machine via the env vars; mis-set vars produce a confusing failure until the resolution layer is documented (R-C5).
  • jb inspectcode against a .slnx has been observed to fail under VS BuildTools 18 (MSB4236) on the sibling project; the jb-inspect step may need a per-.csproj fallback (risk R-C6). NetAnalyzers remains the gating baseline regardless.
  • Enforcing TreatWarningsAsErrors will surface previously-tolerated warnings (notably from the concurrent nullable flip, ADR-0003) that must be driven to zero before the build is green.
  • Removing Source/Properties/AssemblyInfo.cs in favour of MSBuild-generated attributes is a behaviour-equivalent but visible change to how assembly metadata is produced (AC-7).

Published-mod flag (AC-32 / AC-33): the migration is designed to be behaviour- and save-neutral — the Scribe keys and serialized settings shape are held stable. No automated shim is required (backward_compat=none), but if any toolchain change forces a user-visible or save-affecting difference it must be re-flagged here before release.

Alternatives considered

  • Incremental migration across multiple sprints (e.g. SDK conversion first, Harmony bump later) — rejected because the workstreams are tightly coupled (the test project needs the SDK/.slnx; zero-warnings needs the nullable flip) and a partial stack leaves OM unbuildable on the modern toolchain in the interim with little benefit.
  • Keep the legacy non-SDK csproj, add only env-var HintPaths — rejected because the legacy project still cannot run dotnet build / jb and cannot host the SDK-style test project; it would not close the gap to the sibling standard.
  • Stay on Harmony 2.3.6 — rejected because the house standard and the only authored tech-reference target 2.4.2; diverging would require maintaining a lib-harmony-2.3.6 reference solely for OM and break sibling consistency.
  • Check in resolved absolute reference paths instead of env vars — rejected because it reproduces the non-portable, machine-bound build this migration exists to remove.

Related ADRs

ADR-0003 · Production nullable-reference-types migration

Context

The legacy OutfitManager.csproj does not set <Nullable>; nullability intent is carried by a single JetBrains [NotNull] attribute at ApparelCache.cs:24 (a constructor parameter). The house standard (per custom-coding-rules.md and stack.html) requires Nullable enable project-wide with C# nullable-reference-types replacing JetBrains nullability attributes, and the two systems must not coexist. The audit measured OM's annotation surface as trivial — exactly 1 [NotNull], 0 [CanBeNull] — roughly two orders of magnitude smaller than the sibling EM migration (224 attributes / 131 NRT sites). OM already uses modern C# idioms (file-scoped namespaces, collection expressions, target-typed new()), and LordKuper.Common's consumed types (WorkTypeThingRule, ThingCache) are already Nullable enable, so OM's consumption sites largely line up.

Forces: (1) the flip cannot be compile-verified on the legacy csproj (it cannot dotnet build), so the exact warning count is estimated, not measured — bounded well under 20 distinct sites given the ~640 LOC and the idiom baseline; (2) the warnings the flip surfaces concentrate on Scribe-populated static fields (_selectedWorkTypeRule, _workTypeRules) and FirstOrDefault nullable results in ApparelCache / WorkTypeHelper / Settings_WorkTypes; (3) blanket = null! on Scribe-populated fields can mask a genuine null and must be applied judiciously; (4) [UsedImplicitly] (4 occurrences across 3 files) is not a nullability attribute and must be preserved along with its using JetBrains.Annotations;.

Decision

Enable Nullable enable on the production project and resolve all surfaced NRT sites green under TreatWarningsAsErrors. Replace the lone [NotNull] at ApparelCache.cs:24 with a real non-nullable parameter type (ThingCache's base constructor already throws ArgumentNullException on null, so the runtime contract is preserved) and remove using JetBrains.Annotations; from ApparelCache.cs (it carries no other JetBrains attribute). For Scribe-populated collection fields (_workTypeRules), declare them nullable and initialize with ??= in the init path per custom-coding-rules.md, rather than blanket null!; for legitimately-nullable scalars/locals (the FirstOrDefault results), use ? plus a guard. The [UsedImplicitly] attributes and their using directives in the other three files are left untouched. JetBrains nullability attributes and C# NRT must not coexist.

Consequences

Positive

  • OM's nullability intent is expressed in the compiler-checked NRT system rather than advisory attributes, matching the house standard and the consumed Common surface (AC-12).
  • The migration surface is tiny (1 attribute, est. <20 sites) — low risk and quick relative to the sibling EM migration.
  • Removing the lone JetBrains nullability attribute eliminates the forbidden two-systems coexistence while preserving the runtime null-guard via the Common base ctor.
  • The flip is gated by the new W6 tests and TreatWarningsAsErrors, so a mis-applied annotation is caught rather than shipped.

Negative

  • The exact warning set is estimated, not measured — the legacy csproj cannot compile-test the flag, so the true count is only known after ADR-0002's SDK conversion lands (the two are sequenced).
  • Blanket = null! on Scribe-populated fields, if used carelessly, can hide a genuine null and defeat the purpose; the chosen ??=/guard approach is more verbose and must be applied per-field with judgement (risk R-C4).
  • Touching the Scribe-populated static fields risks an inadvertent change to load/save behaviour if the initialization path shifts — must be characterization-tested to preserve save compatibility (AC-32).
  • Adds a small ongoing obligation: future Common upgrades that change nullability annotations on consumed types may surface new OM warnings under TreatWarningsAsErrors.

Published-mod flag (AC-32): the nullable flip must not alter the serialized shape of _workTypeRules / WorkTypeScoreFactor — the ??= init for the Scribe collection is specifically chosen to keep load behaviour identical to the current default-seeding path; verified against the W6 characterization tests.

Alternatives considered

  • Keep JetBrains nullability attributes, do not enable NRT — rejected: violates the house standard, leaves nullability advisory rather than compiler-checked, and would block the zero-warnings/standard-conformance goal.
  • Blanket = null! on every Scribe/reflection-populated field — rejected as the default: it silences the compiler without expressing real intent and can mask genuine nulls; reserved only for fields that are guaranteed-populated-before-use by the framework, with ??=/guards preferred for collections.
  • Annotate per-file / per-region incrementally (#nullable enable islands) — rejected because OM is small enough to flip project-wide in one pass; partial islands add ceremony and leave an inconsistent codebase.
  • Defer the nullable flip to a later sprint — rejected: it is a headline W3 workstream and the migration surface is trivial; deferring would leave the project half-aligned and the zero-warnings gate unreachable.
