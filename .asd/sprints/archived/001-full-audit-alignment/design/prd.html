Outfit Manager — Alignment PRD

3 goals · 7 stories · 33 AC · 6 non-goals · updated 2026-06-07

Problem

OutfitManager (OM) is a published RimWorld mod that still runs on the legacy build stack — non-SDK .csproj, packages.config, Harmony 2.3.6, no test project, no Nullable. Its sibling mods (EquipmentManager as the reference) have already moved to the modernized LordKuper house standard. The structural, technical, and quality gap between OM and that standard makes OM harder to maintain, impossible to build portably or under the modern dotnet/jb flow, and unverifiable for regressions. This sprint brings OM into full alignment with the modern sibling standard in a single end-to-end pass, without changing the mod's observable behaviour.

Goals

  1. G1

    Structural & stack alignment. Restructure every project to the modern sibling layout and migrate the full build/test stack (.slnx, SDK-style projects, PackageReference, .NET 10 SDK / dotnet / jb, Nullable enable, zero-warnings, Harmony 2.4.2, LordKuper.Common 1.6, NetAnalyzers 9.0.0 pin) so OM builds end-to-end on the modern stack.

  2. G2

    Quality & reuse. Eliminate any duplication of LordKuper.Common functionality in favour of shared-library reuse, simplify and optimize hot paths without changing observable behaviour, and stand up the unit test project with initial coverage of the migrated/refactored logic.

  3. G3

    Rule & published-mod conformance. Bring OM into conformance with the project rule set (zero-warnings, language policy, coding conventions), and ensure any user-visible or save-affecting change is explicitly flagged for the published player base.

User stories

  • as the mod maintainer, I want the full build/test stack migrated to the modern target, so that OM builds portably under dotnet/jb with zero warnings on any machine. US-3
  • as the mod maintainer, I want OM verified against the project rule set, so that the codebase provably conforms to the house standard before release. US-7

  • as a contributor, I want a unit test project with isolation and assembly-resolver infrastructure plus initial coverage, so that I can safely change the scoring/cache logic and catch regressions. US-6
Player 1

Non-goals

  • EM-only systems OM does not have — StatDefs, loadout/weapon scoring, and SimpleSidearms integration are NOT added to OM.
  • Optional-mod integrations — no SimpleSidearms / Combat Extended / VFE soft-ordering or compatibility is added (OM is integration-free by design).
  • UX / UI change — no UX spec is produced this sprint and no UI change is made; OM's settings window (General + Work Types tabs) is unchanged. This is an alignment/migration sprint, not a feature sprint.
  • Workflow infrastructure — .asd/ and .claude/ directories (rules, templates, agents, skills, hooks, config) are not modified by this sprint's product work; the stale "current vs target" caveats in custom-*-rules.md are post-sprint housekeeping (DM-7).
  • LordKuper.Common itself — the upstream shared library is consumed, not modified; any gap is reused-around or noted, not patched here.
  • Persistent requirements doc — no design/product/requirements.html is produced; no new user-facing behaviour is introduced, so there is no feature set to capture as a persistent requirements artifact.

Assumptions & dependencies

  • The EM sprint-001 shape is the structural and procedural reference, adapted to OM's narrower (integration-free) feature surface.
  • OM's two upstream compile-only dependencies — LordKuper.Common 1.6 and Lib.Harmony (target 2.4.2) — are consumed, not forked; RimWorld Assembly-CSharp + Unity modules are game-bound HintPath references resolved via env vars after W3.
  • A green dotnet build and the in-game patch-applied verification depend on the game assemblies and rimworld-common being resolvable on the build machine (see audit R-C5).
  • The persistent design/ docs (concept, stack, 12 tech-references) already describe the TARGET standard; this sprint makes the code catch up, after which the "current vs target" framing is reconciled (audit DM-1, DM-2). Those reconciliations are tracked in the documentation migration plan, not in this PRD.
